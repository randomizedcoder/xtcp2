# Go-native RDMA implementation status

Last updated: 2026-10-18.

**R0, R1, R2 and R4 done: 17 of 20 implementation tasks passed their gates; R3 is deferred.**
R0 built the groundwork: the ABI layout guard, capture tooling, captured
testdata, parsing guards and the cgo baseline. R1 replaced verbs async events
with netlink: GET_CHARDEV and NLDEV codecs, the port map and translator, and
the netlink event source, whose path is allocation-free. R2 replaced
libibumad with a native umad exchange: 416 B and 1 allocation against 512 B
and 2, with no process-wide lane. R4 made the native paths the default
(R4-T01) and then the only ones (R4-T02): go-link-monitor is one
`CGO_ENABLED=0` binary with no `NEEDED` entry and no rdma-core in its closure,
and parse-guards keeps every go-link-monitor package cgo-free. R4-T03's final
review ran the native benchmarks in the performance VM and, with the
operator's approval, on `l`'s mlx5 host, together with start-up timing
against the last cgo build and the recorded-events test against mlx5. The
review also dropped the source tree from the package's runtime closure
(149 MiB to 33 MiB). R3, verbs-level events from provider contexts, stays
deferred until a fleet driver needs it. The results are in
[Go-native performance findings](#go-native-performance-findings).

This tracks [GO-NATIVE-RDMA-IMPLEMENTATION-PLAN.md](GO-NATIVE-RDMA-IMPLEMENTATION-PLAN.md)
for the design in [GO-NATIVE-RDMA-DESIGN.md](GO-NATIVE-RDMA-DESIGN.md). It is
separate from the main [STATUS.md](STATUS.md), and `test-linkmonitor-docs`
checks it against the plan in the same way.

## Update rules

- Task and phase states are exactly `not started`, `in progress`, `blocked`,
  `done` or `deferred`.
  - `blocked` needs a concrete cause and an unblock action.
  - `deferred` needs an explicit scope decision.
- A checkbox is checked only for `done`.
- At the start of a session, pick a task whose dependencies are done and set
  it to `in progress`. At the end, record evidence, blockers and the next
  action, even if the task is not finished.
- Mark a task done only when its "Done when" gate passes, using the Nix
  command the plan names. Skipped or unavailable checks are unverified, not
  passed.
- Evidence ids are `RV001`, `RV002` and so on. They are separate from the main
  status document's `Vnnn`. Append reruns; never overwrite a failure. Record
  the date, command, host or VM, kernel, base revision, outcome and where the
  logs are kept.
- Changes to scope or dependencies update the plan and this document together,
  keep task ids stable, and are explained in the log.
- Changes on host `l` (address triggers, `modprobe ib_umad`, live runs) need
  the operator's approval at the time. Record the approval in the evidence
  row.

Why the go-native paths are cheaper, as the profiles show:

- **No cgo transition.** In R0-T05's profiles `runtime.cgocall` and its
  syscall entry and exit take about 90% of `BenchmarkPerformanceCGO`'s CPU. The
  native decoders are plain Go functions the compiler inlines into the caller
  (`PortMap.find` is inlined), so that cost is not paid at all.
- **Header-only decoding.** The translator reads the 16-byte `ifinfomsg` or
  8-byte `ifaddrmsg` header and stops, because a port's Refresh or Topology
  needs only the ifindex and two flag bits. The existing decoder walks every
  attribute (`xtcpnl.ParseNewLink` and `ParseMonitorLink` lead its CPU profile)
  to build a full link record.
- **No allocation.** Results go into a caller-owned `[MaxPorts]Event` array and
  device names are shared from the port map, so the hot path never calls
  `mallocgc`. `TestTranslateAllocs` and parse-guards hold it at 0.
- **No bounds checks in the loop.** The decoders carry `_ = b[n]` hints, and
  parse-guards fails the build if a check appears outside one.
- **Lookups without hashing.** The port map is a sorted slice searched in place,
  so each lookup is a few comparisons with no map hashing or
  interface conversion.

Profile check: the CPU tops for `native-rtnl` and `native-chardev` hold only
`rdmanative` and `xtcpnl` frames, with no `mallocgc`, `reflect` or `convT`.
The `mallocgc`, `protoregistry` and `compress/flate` lines in the heap tops
are the test binary's start-up and the profiler itself (4.4 MB in total over
about 24 s, none under a benchmark frame).

R1-T06 measured the whole path rather than the decode alone (RV051).
`BenchmarkEventPath` writes one `RTM_NEWLINK` datagram per port into a
`SOCK_SEQPACKET` pair. The source's end receives as `nlconn.Conn` does: park in
the runtime poller for the first datagram, then drain without waiting, up to 64.
Each batch then goes through the envelope walk, the translator and emit, which
hands it to the benchmark goroutine as the monitor's worker would take it.
What the profile shows:

- **The kernel dominates.** `Syscall6` is 60% of CPU: the benchmark's own
  `write` (30%) and the source's `recvmsg` (32%). The futex and scheduler
  frames of the cross-goroutine wake-up are most of the rest, which is why
  batch=1 costs 6.2 µs and batch=64 1.3 µs per event: the wake-up is paid once
  per batch. The translator (`Translator.link`) is 1.4%.
- **The cgo baseline is not the same measurement.** `BenchmarkPerformanceCGO`
  copies events already queued in C memory, so it pays neither a syscall nor a
  wake-up. A verbs async event also costs a `read` on the async descriptor
  (`ibv_get_async_event`) and a thread wake-up, so the like-for-like cgo
  number is the same kernel cost plus the cgo call. The native path's own CPU,
  the translator, is the 15 ns per message of the R1-T03 row.
- **The allocations are in the receive layer, not the decoders.** 9 allocs at
  batch=1, then 5 per datagram (320 at 64). The heap profile puts all of them in
  the receive mirror: `unix.Recvmsg` (63% of bytes) returns a new
  `unix.Sockaddr` per datagram, and the `attempt` and `Control` closures with
  the variables they capture (`n`, `recvErr`) escape to the heap (37%).
  `nlconn.receiveOne` has the same shape (it also captures `flags` and
  `from`), so the existing rtnetlink listener pays it too. `Source.Run` builds
  its one closure once per `Run` (escape report: `source_linux.go:61-62`), and
  the translator allocates nothing.
- **The decoders' escape and BCE reports are clean.** No `rdmanative` decoder
  line escapes. The BCE report's only entries are the allowlisted
  `rdmacaps/query.go` and `xtcpnl.go` lines from before this work.

That failed the plan's "no `mallocgc` in the pprof top" condition (about 7%
cumulative), so the operator chose to fix the receive layer in `nlconn`
(RV053, RV054):

- **The sender lands in the Conn, not a new Sockaddr.** `recvmsgNetlink` calls
  `recvmsg(2)` with a stack `Msghdr` whose name points at a
  `unix.RawSockaddrNetlink` held in the `Conn`. A short address (a non-netlink
  peer) leaves it zeroed, so the kernel-only sender check still rejects it.
- **The callbacks are bound once.** The receive state (length, flags, error,
  the context's done channel) lives in the `Conn`, which has a single I/O
  owner, and the `Read` and `Control` callbacks are built on first use. Nothing
  escapes per datagram. `TestReceiveAllocs` holds a 64-datagram `Receive` to
  the allocations of a one-datagram one, and `recvmsgNetlink` to zero.

After the change the event path allocates nothing and is 28-39% faster per
event (4.45 against 6.16 µs at batch=1, 0.78 against 1.28 µs at batch=64), and
its CPU and heap tops hold no `mallocgc` under a benchmark frame (the heap top
is the profiler's own start-up). The existing rtnetlink listener, through
`pkg/rtnlmon` and `linuxio`, gets the same saving per notification.
`nlconn.Conn.Receive` then kept 5 allocations (280 B) per call, whatever the
batch size, all from the cancellation hook `operation` registers with
`context.AfterFunc`. Two more changes removed most of them (RV056, RV058):

- **The hook is built once per `Conn`.** The function that closes the `Conn`
  and the channel it reports on are `Conn` fields, created on first use.
  Reuse is safe because `operation` reads that channel whenever the hook's
  stop function reports it already ran, so it is empty again before the
  next operation. `TestCancelHookReuse` checks this, including a cancel
  during an operation.
- **A context that can never be canceled registers nothing.** When
  `ctx.Done()` is nil (`context.Background()`), `operation` skips
  `context.AfterFunc`.

What is left is `context.AfterFunc`'s own registration: 2 allocations,
128 B per call with a cancelable context, and none with a background one
(`r1-t06/vm-hook`). A `sync.Pool` would not help here: what was allocated
was closures, a channel and the runtime's registration, not buffers.
`r1-t06/vm-hook` is cited for allocations only. `l` was running other work
during that run (load average about 22 on 24 CPUs), and the event path,
which this change does not touch, varied by up to ±151%. The first run's raw output is in the
session scratchpad only: the runner now also requires `native-receive`, so it
cannot be promoted, and evidence is never copied by hand.

In R2-T03's umad row (RV072), the cgo `BenchmarkPerformanceUMAD` simulates
the exchange, with three cgo calls and no I/O. The native `BenchmarkUMADExchange` makes real system calls
against a `SOCK_SEQPACKET` fake device and its scripted peer: write, poll and
read per exchange, plus the peer's. So only bytes and allocations compare. On
hardware, either path is dominated by the MAD round trip to the subnet
management agent (microseconds to milliseconds), not by these costs.

- **Allocation.** The one allocation is the `umadExchange` block (packet,
  registration, chardev), since interface calls let their arguments escape.
  The heap top shows only `exchangeUMAD`. The codec itself allocates nothing
  (`EncodeUMADRequest` 15.4 ns, `DecodeUMADReply` 14.0 ns,
  `EncodeRegisterAgent2` 2.7 ns, all 0 B).
- **Concurrency.** The cgo path serializes on `umadLane`, so a contended query
  costs 86% more than an uncontended one. The native exchange owns its
  descriptor and agent, and contention adds 4%. `TestNativeSkipsUMADLane`
  checks that the native path never waits on the lane, and the rxe guest's
  `parallel_native` row runs eight queries of one port at once.
- **Timings are noisy.** `l` carried other work during the run (load average
  5-9 on 24 CPUs), so the native timings are cited only for the contention
  ratio.

### Final review (R4-T03)

The assessment's six-step review plan, step by step:

1. **Baseline.** R0-T05 (RV028-RV031) measured the cgo paths in the VM and on
   `l`, and its raw output is committed. Since R4-T02 there is no cgo build to
   rerun, so `bench-linkmonitor-rdma-native --baseline` compares against
   those files.
2. **Per-change benchstat.** R1-T03, R1-T06, R2-T03 and R4-T03 each committed
   a benchstat run. The cgo benchmarks copy or simulate in memory with no
   system call, so against them only B/op and allocs/op are comparisons; the
   runner now writes that on the first line of both comparison files, and
   the bench gate checks it is there. The native timings are compared with
   the native runs before them: R4-T03's VM figures match R1-T06's and
   R2-T03's, so R4-T02's removal changed nothing on the native paths.
3. **Profiles.** No CPU top in `r4-t03/vm` or `r4-t03/l` has `reflect` or
   `convT`. The only `mallocgc` line is the umad exchange's one documented
   allocation in the VM (0.7% cumulative); none appears on `l`.
4. **Escape and BCE reports.** `test-linkmonitor-parse-guards` passes
   (RV093): no decoder line escapes, every bounds check is allowlisted, and
   the allocation tests hold the decoders, the umad exchange and the codec at
   their budgets.
5. **Real hardware.** Approved by the operator on 2026-10-18. The native
   benchmarks ran on `l`, which also covers R1-T06's live run, and the
   decoders keep their VM ratios. `TestRDMAEventsRecorded` passed all eight
   rows against `l`'s mlx5_1 (RV091). mlx5 adds a Topology to every link
   change: the address and route changes that come with a flap, which the
   rows allow, since an extra Topology is a resync and never a missed change.
   Native InfiniBand PortInfo replies stay unverified, since no host here has
   an IB link layer.
6. **CI guard.** The gates already run every benchmark in
   `test-linkmonitor-rdma-native-bench`'s smoke run, the decoder and umad
   allocation tests in parse-guards, and `nlconn`'s `TestReceiveAllocs` in the
   unit leaf. The full host `bench-linkmonitor` was not run on `l` (not part
   of the approval); the performance VM ran the monitor's own benchmarks.

**What go-native bought.** One static binary instead of two builds; a
runtime closure of 4 paths and 34.5 MB instead of 23 paths and 155 MB (before
counting the source tree, which both carried until this review); no shared
library or provider `dlopen` at start (the rxe VM's strace check, RV086);
7% less RSS at start-up and 10% faster process start; RDMA events with no
verbs context, so no hardware resources per monitor and device removal that
never waits on the monitor; an allocation-free event path; and a umad
exchange with half the allocations and no process-wide lane. The event
path's cost is the kernel's: a `recvmsg` and a goroutine wake-up per batch,
microseconds per event against an event rate of a few per link change.
