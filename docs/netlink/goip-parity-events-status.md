## Decision log

- **Decided: the event corpus is rows in the workbench, not a rebuilt `nlmon-capture` oneshot (2026-11-13, from the plan's own findings).** The oneshot's shape is the recorded reason the driven machinery exists ("a rebuild per attempt makes that a chore rather than a question"; no stop path), and every corpus since the addr plan has been rows. The oneshot's retirement is a follow-up decision, not this increment's.
- **Decided: addrlabel, neightbl and linkprop *events* are exclusions with reasons, measured in the kernel tree (2026-11-13).** `net/ipv6/addrlabel.c` has no notify; `net/core/neighbour.c` answers `RTM_SETNEIGHTBL` with an ACK only; `rtnl_linkprop` notifies an `RTM_NEWLINK` with `IFLA_PROP_LIST` (`net/core/rtnetlink.c:4503`). The rows that exist are the altname `RTM_NEWLINK` event and the write-request rows.
- **Decided: crafted `.nl` blobs live in `internal/goip/testdata/monitor/`, not `pkg/xtcpnl/testdata/` (2026-11-13).** The "positive fixtures are real captures" rule holds for pcaps; the blobs are inputs the kernel cannot produce, the bond note's carve-out, and are replayed through both tools' `monitor file` paths, which is the only place they mean anything.
- **Found while writing the notes: `print_proto_down` can be crashed, not just misprinted (2026-11-13, DOC036).** The reason gate tests `tb[2]` (the link's `IFLA_BROADCAST`) instead of the just-parsed `preason` table, so it is the only thing standing between the code and `rta_getattr_u8(NULL)` — `*(__u8 *)(NULL + 4)` — on a message whose reason nest lacks `VALUE` while the link carries `IFLA_BROADCAST`. No corpus row can hold it (every linkpd link carries IFLA_BROADCAST and the kernel always sends `VALUE`); it is recorded in [upstream/iproute2-print-json-bugs.md](upstream/iproute2-print-json-bugs.md) and is exactly what EP2's crafted rows exist to exercise.
- **Found while writing the notes: `protodown_reason_tab[32]` shares the off-by-one (2026-11-13, DOC036).** `rtnl_tab_initialize_dir("protodown_reasons.d", protodown_reason_tab, 32)` with the table declared `[PROTODOWN_REASON_NUM_BITS]` (32) — a `32 foo` line writes one past. Measured into [upstream/iproute2-rt-names-table-load.md](upstream/iproute2-rt-names-table-load.md)'s table of callers.
- **Decided: the padding fix is this project's own, so its note is a record, not a series to send (2026-11-13, DOC036).** `c5b76cbb` (2026-11-09) is authored here and sits in the iproute2 tree untagged; [upstream/iproute2-rta-addattr-uninit-padding.md](upstream/iproute2-rta-addattr-uninit-padding.md) records the sightings, the bytes and the O5 tolerance it justifies, and notes that the first release carrying it retires the bug.
- **The check's first red run caught five pre-existing docs faults, all fixed in the same task (2026-11-13, V376).** Two stale anchors in `coverage-status.md` (`nine`/`six` vs the headings' `ten`/`five`), V202's link to the since-merged `render/link_xstats_test.go`, `link-state-tracking.md`'s links into the since-folded `nix/netlink-capture/` tree, and the bond note's shorthand `#decode-side` anchor. Findings are fixed in the docs, never by weakening the checker — the same rule as lint-baseline.
- **Found: `xtcp2-nl-ipmon` was missing from `xtcp2-nlcap`'s passthru, so it had no hermetic rows at all (2026-11-13, V377).** The passthru comment named the helpers vm-lib-exp runs and left ipmon out. EC0-T01 adds it, and with it ipmon's first ten rows — before this, ipmon's only coverage was the capture runs themselves.
- **Found: a canary join that fails ends `xtcp2-nl-ipmon` at `ip`'s own exit, not after the ten tries (2026-11-13, V377).** `writeShellApplication` runs the helper under errexit, and the canary's `ip addr add` is unredirected, so a device that does not exist fails the helper on the first try with ip's own rc and message. That is honest guest behavior (a row bug, named loudly and fast); the boundary row pins it instead of the "never printed the canary" message the first draft expected.
- **Decided: `NLCAP_BRIDGE` still wins the monitor for `xtcp2-nl-brmon`; `NLCAP_IP_BIN` must hold `bridge` when it does not (2026-11-13, V377).** The stand-in seam keeps its precedence so the hermetic rows need no change; an iproute2 bin always holds both binaries, and the helper refuses a directory that holds neither.
- **Decided: the ev seeds are the rtnl-write corpus's four event rows, ported whole (2026-11-13, V378).** Their pre steps, triggers, until-EREs and floors (14, 20, 11, 36) are measurements the corpus already made, so `ev.rows.jsonl` is a probe file, not a guess: EC1's probe batch runs it twice and its own counts become the floors the corpus keeps. The plan's EC0-T02 rule — floors and EREs from measurement — is met by porting measurements, and the probe renews them.
- **Decided: the ev floors are the minimum over both contexts a row runs in (2026-11-24, V379).** The batch's default `-j 8` runs the four monitors in parallel on one guest, and that load is what races the canary join ahead of the monitor's subscription (`ev/nsid-del`: 16 alone, 22-31 in the batch, the helper's join retry adding the del/re-add pair and two GETNSID roundtrips). A floor set from the batch shapes alone would refuse the row's clean shape: anycast-del's first renewal used 31 (batch-only) and a single-row sample then measured 25 under it. So every ev floor is the minimum observed across `run` and `batch` alike — 16, 25, 11, 54 — and the raced captures are kept: they are the helper working, real iproute2 behavior, above the floor.
- **Found while writing the EC1 tranche (2026-11-24, V380): `ip monitor`'s init probe is answered EINVAL at random under concurrent namespace churn — a kernel race.** `ipnetns_have_nsid` (ip/ipnetns.c:67) probes `RTM_GETNSID` for the monitor's own netns; the kernel's `rtnl_net_getid` uses the non-allocating `peernet2id` (net/core/net_namespace.c:358), and `preinit_net` starts every netns's table empty — so the EINVAL of an unassigned self-id is the DEFAULT answer, one iproute2 itself expects ("Continuing anyway"). The diag rows proved more: with the self-id assigned in the pre and still present in the trigger's own `ip netns list-id` inside the window, the probe was STILL answered EINVAL — but only when another row's `ip netns add/set/del` ran concurrently (the reproducer: nsid-del + seven anycast copies as an 8-row batch, two of eight EINVAL in one run; eight copies without the churn row: zero). `unhash_nsid` holds each table's `nsid_lock` and the probe walks under RCU, so the race is not a torn walk — the mechanism is unproven and left for a follow-up, with the reproducer in this entry. The corpus consequence: every ev row is serial (no concurrent churn, deterministic window) and every ev pre-step assigns the self-id (`ip netns set "$(ip netns identify $$)" 0`), so the probe is answered with the id and `netns_map_init` proceeds; everr's serial window is the proof shape — probe→88, canary, the trigger's `RTM_DELROUTE`, and one genuine `NLMSG_ERROR ESRCH`.
