# goip ↔ `ip` lightweight-tunnel encap: implementation status

**Last updated:** 2026-11-04

**Summary:**
- The design and the task plan are in [goip-lwt-encap.md](goip-lwt-encap.md). This document tracks progress against them.
- The plan is written (DOC001). It follows [goip-live-forms.md](goip-live-forms.md), which is closed ([its status](goip-live-forms-status.md)). goip builds `encap` `mpls`, `ip` and `ip6`, with the tunnel options, for a route, a hop and a nexthop object. A 27-form `lwt` workbench family checks it, followed by goip-parity rows and a VM gate.

- LE1-T01 is done: `pkg/xtcpnl/xtcpnl_lwt_ip.go` encodes `encap ip` and `ip6`, with the geneve, vxlan and erspan options. `PutLwtEncap` covers it and `mpls`, and `EncodeLwtEncap` gives a route's or a hop's two `RouteAttr`s. The tunnel flags go out big-endian. `TestPutIPEncap`'s goldens are hand-built from the uapi numbers (V001–V003).
- LE1-T02 is done, and LE1 is closed: `lwtEncapArgs` in `internal/goip/lwt_encap_args.go` reads `encap mpls`, `ip` and `ip6` as `lwt_parse_encap` does, and the nexthop object's `encap` uses it (`ip`/`ip6` there still refuse until LE2-T02). `dst any` and `dst all` send an empty address, as `get_addr` gives them (V004–V006).
- LE2-T01 is done: a route's `encap` (`routeArmEncap`) and a hop's (`parseOneNh`) go where the keyword is, from `internal/goip/route_write_encap.go`. ip's two buffer bounds are refusals. O5's two fibt rows moved from `refuses` to `differs`, and the only difference is `ip`'s stack padding after a hop's `RTA_ENCAP_TYPE`, which LE3-T03 zeroes (V007–V009).
- LE2-T02 is done, and LE2 is closed: a nexthop object's `encap ip` and `ip6` are built, no longer `ErrNotImplemented`, through `EncodeLwtEncapAs` with `NHA_ENCAP` and `NHA_ENCAP_TYPE`, under the same `addraw_l` bound as a route. `mpls`'s rows are unchanged (V010–V012).
- LE3-T01 is done: `nlcapgen matrix -family lwt` writes 39 rows, the 27 forms (21 rc 0, 2 rc 2, 4 rc 255) and 12 duplicate adds, to `nix/microvms/workbench/lwt.rows.jsonl`. The plan's counts were corrected to these (V013–V015).
- LE3-T02 is done: two fresh-boot batches agree on all 39 rows, every rc as written, and the first is the corpus in `pkg/xtcpnl/testdata/7_3_0/ws/lwt*` (V016–V018). The runs' only byte differences are `ip`'s unzeroed padding, in three places LE3-T03's O5 zeroing has to reach.
- LE3-T03 is done, and LE3 is closed. O3 (`pkg/xtcpnl/xtcpnl_ws_lwt_test.go`) checks the 35 captured requests' encaps against their axes, and the 4 rc 255 rows send none. O5 has the four spaces: all 39 rows are `same`, and the two fibt rows moved from `differs` to `same`, now that `wsO5ZeroEncapPad` reaches a route's `RTA_ENCAP`, each hop's in `RTA_MULTIPATH`, and every nest inside them (V019–V021).
- LE4-T01 is done: 23 `gw_lwt*` goip-parity write rows, one per form and ip rc, picked by `TestGwLwtMatrixRows` from the `lwt` rows: the 21 rc 0 forms, and implicit null and geneve's 3 data bytes at rc 2. nlparity now compares `RTA_MULTIPATH` hop by hop past each hop's padding, since the captures show `ip`'s stack bytes after a hop's `RTA_ENCAP_TYPE`. The rows stay ungated until LE4-T02 (V022–V024).
- LE4-T02 is done, and LE4 and the plan are closed. The full run on the main merge, 5599e473, was clean (V025). On 84260fe2, two `--section route,nexthop` runs passed 124 of 124, all 23 `gw_lwt*` rows among them (V026). The full run with the rows gated passed 1330 of 1330 (V027). The 23 rows are in `gated_commands` and `TestAllowlistCommitted`'s earned list, and the GW matrix tables' gated check and `TestUngatedSurfaceIsNotVacuous` no longer skip `gw_lwt*` (V028–V029).

**Next action:** none in this plan. The other encap types, all but `bpf`, are planned in [goip-lwt-srv6.md](goip-lwt-srv6.md) and tracked in [its status doc](goip-lwt-srv6-status.md).

## Decision log

- **`mpls`, `ip` and `ip6` first, with their options.** They're the types goip's corpus already has (`kwnh`, the two fibt rows), and they share one grammar. The others each bring a structure of their own and get a follow-on plan, in the selftests' order of use.
- **One encoder for three places.** A route's, a hop's and a nexthop's encap are the same `lwt_parse_encap` writing to different attribute types. A single `lwtEncapArgs` keeps their parsing identical, as `ip`'s is.
- **goip refuses an encap over `ip`'s 1024-byte route bound, rather than dropping it.** `ip` prints `addraw_l`'s error and sends the route without its encap, because `iproute_modify` ignores the return. Sending a route the user didn't ask for isn't parity worth having. No form reaches the bound.
- **The tunnel flags are big-endian.** `TUNNEL_KEY`, `TUNNEL_CSUM` and `TUNNEL_SEQ` are `__cpu_to_be16`, and `rta_addattr16` writes them as they are, so `key csum seq` sends bytes `00 0d`.
- **Refusals exit 1, as goip's other route and nexthop arms do.** `ip` exits 255 for them; goip's `invargErr` wraps `ErrInvalidArgument`, and only `ErrLinkUsage` maps to 255. So an encap refusal is an O5 row, not a goip-parity pick.
- **geneve's class and type are base 0, like `ip`'s `get_be16` and `get_u8`.** `0102` is octal 66 and `80` is decimal, so the plan's forms write `0x0102:0x80`, and a corner form keeps the base-0 reading.
- **`any` and `all` send an empty address.** `get_addr` gives them a bytelen of 0, and `rta_addattr_l` sends that as an attribute with no payload. `PutIPEncap` accepts an empty `Addr` for DST and SRC.
- **No `getBe*` helpers.** goip reads with its `getU16`/`getU32`/`getU64`, and xtcpnl writes big-endian, so the byte swap lives in one place.
- **A route's bound is `addraw_l`'s, which counts the request so far.** `addraw_l(&req.n, 1024, …)` checks the aligned message length plus the encap against 1024, so the header, the rtmsg and every attribute before `encap` count, which is tighter than the 1020 bytes `buf[1024]` holds. goip refuses with `addraw_l`'s message; `ip` prints it and sends the route without the encap.
- **A hop's bound is what is left of `parse_nexthops`' 4096 bytes.** The `RTA_MULTIPATH` header, the earlier hops, this hop's `rtnexthop` and its attributes so far count. Over it, `parse_one_nh` fails and `ip` exits 255 with "Error: cannot parse nexthop"; goip refuses with the same text, and exits 1 as its other refusals do.
- **LE2's capture rows wait for LE3.** The plan's "each `lwtroute4`, `lwtroute6`, `lwthop` form" (LE2-T01) and "each `lwtnh` form" (LE2-T02), byte for byte, need the captures LE3-T02 makes, so LE3-T03's O5 rows check those forms, and `TestRouteWriteEncap`'s and `TestNexthopWriteEncapIP`'s expected bytes are hand-built.
- **A nexthop object's bound is a route's.** `ipnh_modify`'s encap is the same `buf[1024]` and `addraw_l(&req.n, 1024, …)`, so the header, the nhmsg and the attributes before `encap` count. `EncodeLwtEncapAs` gives the encoder the two `NHA_*` types, so the three places share one encoder.
- **The plan's counts were off by the base-0 form.** Adding "`ip` `geneve_opts`, base 0" made 27 forms but moved the count to rc 2 rather than rc 0; the forms are 21 at rc 0, 2 at rc 2 (implicit null, geneve data of 3 bytes) and 4 at rc 255. `deriveDupGone` takes three duplicates from each of the four spaces, 12, not "up to 9".
- **A tunnel's id is `tun_id` in the axes.** `LWTUNNEL_IP_ID` and a nexthop object's own id are both `id` on the command line. With both under `id`, `nhHasID` took the tunnel's 1 for the nexthop's and skipped `ip6`'s duplicate, which has no tunnel id. O3 reads `tun_id` and `hopN_tun_id`.
- **O5's zeroing has to reach inside the options.** The second boot's bytes differ from the first's in the padding after geneve's `CLASS` (2 bytes) and `TYPE` (3 bytes), two nests below `NHA_ENCAP`, as well as after a route's and a hop's `RTA_ENCAP_TYPE`. So `wsO5ZeroSubPad`, which walked one level, now recurses into every `NLA_F_NESTED` attribute inside the encap (LE3-T03).
- **O5 calls an rc 255 encap refusal `same`.** `ip` exits 255 and goip 1 (`invargErr`), and neither sends a request, which is what O5 compares. So the four rc 255 forms can be O5 rows but not goip-parity picks, which need goip to exit 0.
- **nlparity learned `RTA_MULTIPATH`'s hops before the VM run, not after.** The plan said to check `samePastPadding` on a hop row first. But `RTA_MULTIPATH` isn't `NLA_F_NESTED`, so the hop's bytes are compared whole, and the captures already show the two bytes after a hop's `RTA_ENCAP_TYPE` vary (`40 86` in fibt's, and between `lwthop/ec-002`'s two boots). A hop row would pass or fail by the stack's luck. `sameHopsPastPadding` compares each `rtnexthop` header exactly and its attributes past their padding, in route messages only.
- **The full run had the rows gated, as LF3-T02's did.** The plan puts the full run before gating. With the 23 rows in `gated_commands`, a finding on one fails the run rather than being reported as ungated, so a clean run with them gated also covers the plan's order.
